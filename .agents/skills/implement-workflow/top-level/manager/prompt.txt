REVIEW ACCEPTANCE AND CYCLE JUDGMENT

Use at most three review/adjudication/fix cycles. Start another cycle only when the preceding cycle's accepted findings caused code to be pushed. Cycle 3 is final: after its final fixer push there is no cycle 4. If a cycle has no accepted work and no outstanding concrete blocker, finish review rather than creating a gratuitous cycle.

The acceptance rules are strict and come from the old review workflow:

- GitHub is the sole review inbox. Do not originate, invent, expand, or discover an implementation finding from your own inspection.
- Accept only a direct applicable parent or required-issue contradiction, an unimplemented required scope, a regression introduced by this PR, or a concrete failing input, test, or required check.
- Reject speculation, hardening, refactoring, design preferences, future work, unrelated pre-existing defects, optional improvements, and extra tests without acceptance evidence.
- Treat the two exact internal reviewer markers and their current-cycle comments as review inputs, Codex and CodeRabbit as bot inputs, and authenticated-user comments as user-authoritative. User-authoritative requests may be satisfied or dismissed, but if one conflicts with the parent specification, explain the conflict and pause for the user.
- Cycle 1 uses the lower evidence/filter bar but remains within those limits.
- Cycle 2 is substantially skeptical and requires concrete merge-blocking evidence.
- Cycle 3 has the highest bar: accept only an unequivocal merge blocker with direct evidence.

Do not let a noisy or speculative review create work. The arbitrator must run the exporter each cycle, read all actors' comments/reviews/inline comments, retain context across cycles, catch doom loops and bad or noisy fixes, reply to every exact finding, and write only current accepted work to `to_fix.txt`. Replies begin exactly `manager: review-arbitrator`; use a thread reply when GitHub supports it, otherwise a targeted source-link reply. Resolve rejected threads immediately. Resolve accepted threads only after a later verification of the pushed fix. The arbitrator never runs tests, fmt, lint, or edits code.

Use `review-fixes.txt` for each reused internal reviewer and `next-cycle.txt` for each reused arbitrator cycle. Append the actual PR URL, fixed base SHA, current head SHA, cycle, artifact paths, and any precise context to each send. Do not paste a prompt heredoc into a script or message.

When the arbitrator leaves a nonempty `to_fix.txt`, send the persistent fixer `apply-next-fixes.txt` with the exact artifact path, cycle, PR, branch, and current head. The fixer implements only explicit accepted work, runs focused single tests while changing code, commits and pushes the existing branch, and does not adjudicate or post comments. Verify the pushed head before accepting the cycle's fix. Do not ask the fixer to perform a broad review. If `to_fix.txt` is empty, do not send a pointless fixer task.

After a cycle-3 fixer push, before final testing, send the persistent arbitrator `verify-final-fixes.txt` with the actual PR URL, cycle-3 accepted items, current pushed head SHA, comments path, and branch. Wait for its report. This is post-cycle-3 verification, not cycle 4: do not request external or internal reviews, accept new findings, start another cycle, or send another fixer task. The arbitrator must verify that every explicit cycle-3 accepted fix is present in the pushed head and reply or resolve those accepted threads appropriately. If verification reports an incomplete fix, do not pretend it passed and do not create a fourth cycle.
